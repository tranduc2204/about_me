Common Table Expressions (CTE): Nghệ Thuật Viết Modular SQL Dễ Đọc, Dễ Bảo Trì

Trần Đức (Dustin)
📅 Tháng 9, 2026 • ⏱️ 10 phút đọc • Chủ đề: Modular SQL & dbt Architecture

Nếu có một kỹ năng duy nhất giúp phân biệt giữa một người "biết viết vài dòng SQL truy vấn đơn giản" với một Analytics Engineer chuyên nghiệp làm việc trong các dự án dữ liệu lớn (như dbt, Snowflake, BigQuery), thì đó chính là: Tư duy module hóa truy vấn với Common Table Expressions (CTE).

Trong quá khứ, khi đối mặt với các yêu cầu phân tích kinh doanh phức tạp, các lập trình viên thường sử dụng các truy vấn con lồng nhau (Nested Subqueries). Hậu quả là những tệp script dài hàng trăm dòng trở thành một mê cung "Spaghetti SQL" vô cùng kinh hãi, không ai dám sửa đổi vì sợ làm hỏng toàn bộ logic ngầm bên trong.

1. Vấn Đề Của Mê Cung "Spaghetti Subqueries"

Hãy cùng nhìn lại cách viết truy vấn con lồng nhau truyền thống: 

-- 🍝 Mê cung Spaghetti: Phải đọc từ TRONG RA NGOÀI, rất khó debug!
SELECT 
    tier,
    COUNT(customer_id) AS total_users
FROM (
    SELECT 
        customer_id,
        CASE WHEN total_spent > 1000 THEN 'VIP' ELSE 'Standard' END AS tier
    FROM (
        SELECT 
            customer_id,
            SUM(order_amount) AS total_spent
        FROM orders
        WHERE status = 'COMPLETED'
        GROUP BY customer_id
    ) AS customer_spend
) AS customer_tiers
GROUP BY tier;

Điểm yếu chí mạng của cách viết này:

  • Ngược dòng tư duy tự nhiên: Bạn phải cuộn xuống tận tầng sâu nhất ở giữa tệp để đọc logic bảng con, sau đó mới lần mò ngược ra các lớp bọc ngoài cùng.
  • Khó khăn khi gỡ lỗi (Debugging): Bạn không thể dễ dàng chạy thử kết quả của một bước ở giữa mà phải mất công cắt tỉa câu lệnh ra một cửa sổ mới.
  • Không thể tái sử dụng (Reusability): Nếu hai bước phân tích khác nhau cùng cần dùng chung một tập dữ liệu trung gian, bạn buộc phải sao chép lại toàn bộ cụm subquery đó.

2. Cú Pháp WITH & Tư Duy Đường Ống Modular Pipeline

CTE (Common Table Expression), khởi đầu bằng từ khóa WITH, cho phép bạn định nghĩa các bảng tạm thời (Temporary Result Sets) tồn tại duy nhất trong phạm vi thực thi của câu lệnh.

Thay vì lồng nhau như búp bê Nga, CTE cho phép bạn viết câu lệnh theo thứ tự từ trên xuống dưới (Top-Down Execution Flow), như một dây chuyền sản xuất lắp ráp:

[Raw Sources] ➔ [Staging / Clean] ➔ [Intermediate Agg] ➔ [Final Output]

Viết lại bài toán phân tầng khách hàng ở trên bằng CTE:

WITH 
-- Bước 1: Tính tổng chi tiêu của mỗi khách hàng
customer_spend AS (
    SELECT 
        customer_id,
        SUM(order_amount) AS total_spent
    FROM orders
    WHERE status = 'COMPLETED'
    GROUP BY customer_id
),

-- Bước 2: Phân loại phân khúc dựa trên số tiền
customer_tiers AS (
    SELECT 
        customer_id,
        CASE 
            WHEN total_spent > 1000 THEN 'VIP' 
            ELSE 'Standard' 
        END AS tier
    FROM customer_spend
)

-- Bước 3: Tổng hợp báo cáo cuối cùng
SELECT 
    tier,
    COUNT(customer_id) AS total_users
FROM customer_tiers
GROUP BY tier;
💡 Lợi thế vượt trội khi Debug

Nếu bạn muốn kiểm tra xem Bước 1 đã tính đúng hay chưa, bạn chỉ cần tạm thời thay dòng cuối cùng thành SELECT * FROM customer_spend LIMIT 10;. Nhanh chóng, trực quan và không hề phá vỡ cấu trúc code!

3. Case Study Thực Chiến: Phân Khúc Khách Hàng Bằng Mô Hình RFM

Mô hình RFM (Recency, Frequency, Monetary) là bài toán kinh điển mà bất kỳ Data Analyst / Analytics Engineer nào cũng phải thực hiện: 

WITH 
-- 1. Import và làm sạch dữ liệu đơn hàng
valid_orders AS (
    SELECT 
        customer_id,
        order_date,
        total_price
    FROM raw_sales.orders
    WHERE order_status = 'DELIVERED'
      AND order_date >= '2025-01-01'
),

-- 2. Tính toán 3 chỉ số R, F, M cho từng khách hàng
rfm_metrics AS (
    SELECT 
        customer_id,
        CURRENT_DATE - MAX(order_date) AS recency_days,
        COUNT(*) AS frequency_orders,
        SUM(total_price) AS monetary_value
    FROM valid_orders
    GROUP BY customer_id
),

-- 3. Phân nhóm hành vi kinh doanh
customer_segments AS (
    SELECT 
        customer_id,
        recency_days,
        frequency_orders,
        monetary_value,
        CASE 
            WHEN recency_days <= 30 AND frequency_orders >= 5 THEN 'Champions'
            WHEN recency_days <= 60 AND frequency_orders >= 2 THEN 'Loyal Customers'
            WHEN recency_days > 90 AND monetary_value > 2000 THEN 'At Risk VIPs'
            ELSE 'Occasional Buyers'
        END AS segment_name
    FROM rfm_metrics
)

-- 4. Báo cáo phân bổ phân khúc cho Giám đốc Marketing
SELECT 
    segment_name,
    COUNT(*) AS total_customers,
    ROUND(AVG(monetary_value), 2) AS avg_spend,
    ROUND(AVG(recency_days), 1) AS avg_days_since_last_order
FROM customer_segments
GROUP BY segment_name
ORDER BY total_customers DESC;

4. Đệ Quy Với Recursive CTE: Xử Lý Cây Phân Cấp (Hierarchical Trees)

Một sức mạnh đặc biệt mà Subquery thông thường không thể làm được là Recursive CTE (CTE Đệ Quy). Nó được sinh ra để xử lý các cấu trúc dữ liệu hình cây vô hạn cấp, tiêu biểu như:

  • Sơ đồ tổ chức nhân viên và cấp quản lý (Org Chart).
  • Cây danh mục hàng hóa đa tầng (Điện thoại ➔ Smartphone ➔ Phụ kiện ➔ Cáp sạc).

Cấu trúc gồm 2 phần được nối bằng UNION ALL:

  1. Anchor Member (Phần neo khởi tạo): Tìm phần tử gốc của cây (ví dụ: Tổng Giám đốc có manager_id IS NULL).
  2. Recursive Member (Phần đệ quy): JOIN ngược lại chính tên của CTE đó để duyệt xuống các nhánh con cho đến khi hết dữ liệu.
WITH RECURSIVE org_tree AS (
    -- 1. Anchor: Tìm lãnh đạo cao nhất (Level 1)
    SELECT 
        employee_id, 
        name, 
        manager_id, 
        1 AS hierarchy_level
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- 2. Recursive: Ghép cấp dưới trực tiếp vào từng quản lý
    SELECT 
        e.employee_id, 
        e.name, 
        e.manager_id, 
        ot.hierarchy_level + 1
    FROM employees e
    INNER JOIN org_tree ot ON e.manager_id = ot.employee_id
)
SELECT * FROM org_tree ORDER BY hierarchy_level;

5. Bàn Về Hiệu Năng: CTE vs Bảng Tạm (#Temp) vs Subquery

Liệu viết CTE có làm câu truy vấn chạy chậm hơn không? Hãy xem sự khác biệt giữa các hệ quản trị:

Môi trường Cơ chế tối ưu hóa CTE Đánh giá hiệu năng
PostgreSQL (>= v12) Tự động Inlining (gộp thẳng vào execution plan chính) nếu CTE chỉ được gọi 1 lần. Ngang bằng hoàn toàn với Subquery thông thường.
Cloud DWH (Snowflake, BigQuery) Query Compiler tối ưu hóa biểu thức DAG, loại bỏ tính toán thừa. Cực kỳ mạnh mẽ. Chuẩn mực thiết kế bắt buộc khi dựng model dbt.
SQL Server / MySQL Được xem như Non-materialized View nội bộ. Nếu CTE phức tạp được gọi lặp lại 3-4 lần, bảng tạm (#temp) có thể nhanh hơn.
📌 Khi nào NÊN cân nhắc dùng Temporary Table (#temp)?

Nếu bạn có một tập dữ liệu hàng chục triệu dòng cần xử lý tính toán cực nặng, và tập dữ liệu đó phải được tái sử dụng để JOIN ở 4 đến 5 bước hoàn toàn độc lập phía sau trong một Stored Procedure dài, việc lưu tạm vào #temp có đánh Index sẽ mang lại hiệu năng cao hơn. Nhưng đối với 90% các tác vụ phân tích và chuyển đổi dữ liệu hằng ngày, CTE là lựa chọn số 1 về tính sạch sẽ và thanh lịch.

6. Triết Lý Thiết Kế Clean SQL Trong Các Dự Án dbt

Trong quy chuẩn của các kỹ sư dữ liệu làm việc với framework dbt (data build tool), mỗi model SQL luôn tuân thủ nguyên tắc "Single Responsibility Principle":

  • Không bao giờ lồng subqueries lộn xộn.
  • Mỗi CTE chỉ làm đúng một nhiệm vụ (như đổi tên cột, hoặc gom nhóm, hoặc tính toán logic nghiệp vụ).
  • Tầng cuối cùng luôn là một câu lệnh final AS (SELECT ... FROM ...) để người duyệt code (Pull Request Reviewer) có thể hiểu toàn bộ bức tranh chỉ trong 30 giây!
