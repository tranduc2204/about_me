Deep-Dive: Xây Dựng Enterprise Data Platform Với CDC, dlt, Snowflake & dbt Core

Làm sao để đồng bộ liên tục dữ liệu giao dịch bán hàng từ cơ sở dữ liệu quan hệ (OLTP) sang Cloud Data Warehouse với độ trễ tối thiểu mà không gây nghẽn hiệu năng sản xuất? Bài viết này mổ xẻ toàn bộ giải pháp kỹ thuật từ dự án AdventureWorks Data Platform: kiến trúc Change Data Capture, giải thuật khử trùng lặp qua LSN, mô hình hóa Kimball Star Schema và tự động hóa CI/CD với 30 tests.

Trần Đức (Dustin)
Data Platform Architect • Analytics Engineer • Author

Trong các doanh nghiệp bán lẻ và sản xuất hiện đại, dữ liệu giao dịch phát sinh liên tục từng giây: đơn hàng mới được tạo, trạng thái thanh toán được cập nhật, và một số đơn hàng bị hủy bỏ hoặc hoàn trả. Phương thức trích xuất truyền thống — chạy các câu lệnh SELECT * FROM sales quét toàn bộ bảng (full table scan) vào nửa đêm — đã bộc lộ những tử huyệt chết người: gây khóa bảng vận hành (database locks), tải trùng lặp dữ liệu khổng lồ và khiến ban giám đốc phải đợi đến sáng hôm sau mới có số liệu báo cáo.

1. Kiến Trúc Medallion Architecture Khép Kín

Để giải quyết triệt để vấn đề trên, tôi thiết kế nền tảng dữ liệu theo mô hình Medallion Architecture 3 tầng rõ ràng:

PIPELINE ARCHITECTURE // End-to-End Data Journey DIAGRAM 
[SQL Server 2022 CDC]  -- (Transaction Log Stream)
          │
          ▼
    [dlt Python Ingest] -- (RSA Key-Pair Auth / Cursor by LSN)
          │
          ▼
 [Snowflake BRONZE]   -- (Append-Only Raw Archive)
          │
          ▼
  [dbt Core STAGING]   -- (CDC Deduplication: ROW_NUMBER over _start_lsn)
          │
          ├─► [dbt SNAPSHOTS] -- (SCD Type 2: snap_products price changes)
          │
          ▼
   [Snowflake GOLD]    -- (Kimball Star Schema: fct_sales merged + dim tables)
          │
          ▼
   [Metabase BI Tool]  -- (12 Business KPIs & Executive Revenue Dashboards)

2. Kích Hoạt CDC & Trích Xuất Bằng Thư Viện dlt (Python)

Trên hệ quản trị cơ sở dữ liệu Microsoft SQL Server 2022 (chạy trong môi trường Docker Container), tôi kích hoạt tính năng Change Data Capture (CDC) ở cấp độ cơ sở dữ liệu và từng bảng giao dịch:

SQL SERVER // Enable Database & Table CDC T-SQL 
-- Kích hoạt CDC cấp Database
EXEC sys.sp_cdc_enable_db;

-- Kích hoạt CDC cho bảng bán hàng dbo.sales
EXEC sys.sp_cdc_enable_table
    @source_schema = N'dbo',
    @source_name   = N'sales',
    @role_name     = NULL,
    @supports_net_changes = 1;

Khi CDC hoạt động, SQL Server Agent tự động đọc transaction log và ghi nhận các sự kiện thay đổi vào bảng hệ thống cdc.dbo_sales_CT. Mỗi bản ghi được gắn kèm một mã định danh nhật ký giao dịch duy nhất gọi là Log Sequence Number (LSN) (cột __$start_lsn) và mã hành động __$operation (1 = Delete, 2 = Insert, 3 = Update Before, 4 = Update After).

Thay vì sử dụng các dịch vụ trả phí đắt đỏ như Fivetran, tôi ứng dụng thư viện mã nguồn mở dlt (data load tool) của Python. Với dlt, tôi thiết lập cursor tăng dần (incremental cursor) theo cột nhị phân __$start_lsn:

PYTHON // dlt Incremental Ingestion by LSN Cursor PYTHON 3.11 
import dlt
from dlt.sources.sql_database import sql_database

# Định nghĩa cursor LSN tăng dần để chỉ trích xuất các event mới
source = sql_database(
    credentials="mssql+pyodbc://sa:Password@localhost:1433/AdventureWorks",
    schema="cdc"
)
source.resources["dbo_sales_CT"].apply_hints(
    incremental=dlt.sources.incremental(
        '"__$start_lsn"',
        initial_value=b"\x00" * 10
    )
)

# Nạp dữ liệu append-only vào Snowflake Bronze schema
pipeline = dlt.pipeline(
    pipeline_name="adventureworks_cdc_pipeline",
    destination="snowflake",
    dataset_name="bronze"
)
load_info = pipeline.run(source.with_resources("dbo_sales_CT"), write_disposition="append")
print(load_info)

3. Chứng Thực Bảo Mật Chuẩn Enterprise: Snowflake RSA Key-Pair Auth

Trong môi trường doanh nghiệp thực tế, việc sử dụng mật khẩu tài khoản tĩnh (Basic Auth) để nạp dữ liệu là hành vi vi phạm nghiêm trọng quy chuẩn an toàn thông tin. Tôi thiết lập cơ chế RSA Key-Pair Authentication 2048-bit cho người dùng service account DLT_USER trong Snowflake:

  • Khóa công khai (Public Key) được gán trực tiếp vào Snowflake User: ALTER USER DLT_USER SET RSA_PUBLIC_KEY = '...';
  • Khóa riêng tư (Private Key) được bảo vệ bằng mật khẩu mã hóa (passphrase) và lưu trữ an toàn trong biến môi trường hệ thống.
  • Áp dụng nguyên tắc đặc quyền tối thiểu (Least Privilege): Gán quyền qua Role chuyên dụng INGESTION_ROLE, chỉ cho phép tạo bảng và nạp dữ liệu trong schema BRONZE.

4. Giải Thuật CDC Deduplication Trong dbt Staging

Khi nạp theo cơ chế Append-only từ CDC, bảng Bronze sẽ chứa nhiều bản ghi cho cùng một đơn hàng nếu đơn hàng đó trải qua các sự kiện cập nhật trạng thái (Update). Nếu trực tiếp đưa dữ liệu này vào báo cáo, doanh thu sẽ bị nhân đôi hoặc nhân ba (hiện tượng Fan-out sai lệch).

Trong model src_cdc_sales.sql của dbt Core, tôi áp dụng giải thuật khử trùng lặp sử dụng hàm cửa sổ ROW_NUMBER():

DBT CORE // models/staging/src_cdc_sales.sql SQL (SNOWFLAKE DIALECT) 
WITH raw_cdc_events AS (
    SELECT * FROM {{ source('bronze', 'dbo_sales_ct') }}
),

ranked_events AS (
    SELECT
        order_number,
        order_line_item,
        customer_key,
        product_key,
        order_quantity,
        unit_price,
        order_date,
        __$operation AS cdc_operation,
        __$start_lsn AS cdc_lsn,
        -- Đánh số thứ tự sự kiện: Ưu tiên LSN lớn nhất và Seqval mới nhất
        ROW_NUMBER() OVER (
            PARTITION BY order_number, order_line_item
            ORDER BY __$start_lsn DESC, __$seqval DESC
        ) AS event_rank
    FROM raw_cdc_events
    -- Loại bỏ bản ghi UPDATE_BEFORE (operation = 3) để tránh rác
    WHERE __$operation != 3
)

SELECT
    order_number,
    order_line_item,
    customer_key,
    product_key,
    order_quantity,
    unit_price,
    order_date,
    CASE WHEN cdc_operation = 1 THEN TRUE ELSE FALSE END AS is_deleted
FROM ranked_events
WHERE event_rank = 1;
"Giải thuật này đảm bảo tính đúng đắn 100%: Dù một đơn hàng bị sửa đổi 10 lần trong ngày, tầng Staging chỉ xuất ra đúng 1 trạng thái mới nhất. Nếu đơn hàng bị xóa (operation = 1), cờ 'is_deleted' được bật để xử lý soft-delete tại tầng Fact."

5. Theo Dõi Lịch Sử Biến Động Giá Với dbt Snapshot (SCD Type 2)

Trong kinh doanh bán lẻ, giá bán sản phẩm (Unit Price) và chi phí vốn (Standard Cost) thay đổi theo thời gian. Nếu báo cáo tài chính sử dụng giá bán hiện tại để nhân với số lượng đơn hàng đã bán cách đây 2 năm, doanh thu lịch sử sẽ bị sai lệch hoàn toàn.

Tôi cấu hình dbt Snapshot để triển khai Slowly Changing Dimension (SCD Type 2) trên bảng sản phẩm (snap_products):

DBT SNAPSHOT // snapshots/snap_products.sql SQL / JINJA 
{% snapshot snap_products %}

{{
    config(
      target_schema='gold',
      unique_key='product_key',
      strategy='check',
      check_cols=['product_price', 'product_cost', 'product_name']
    )
}}

SELECT 
    product_key,
    product_name,
    model_name,
    product_cost,
    product_price
FROM {{ ref('stg_products') }}

{% endsnapshot %}

dbt tự động sinh các cột dbt_valid_from và dbt_valid_to. Khi nối (JOIN) với bảng Fact Sales, hệ thống sử dụng phép so sánh ngày order_date BETWEEN dbt_valid_from AND COALESCE(dbt_valid_to, '9999-12-31'), đảm bảo từng đơn hàng luôn được tính đúng mức giá tại chính xác thời điểm phát sinh giao dịch.

6. Kimball Star Schema & Incremental Merge Trên Fact Sales

Tại schema GOLD, dữ liệu được tổ chức chuẩn Kimball Star Schema:

  • Fact Table: fct_sales (23,935 dòng đơn hàng). Áp dụng chiến lược incremental_strategy='merge' với khóa chính unique_key=['order_number', 'order_line_item']. Khi dbt chạy định kỳ, chỉ những đơn hàng phát sinh mới hoặc có thay đổi trạng thái mới được nạp vào, tiết kiệm 95% chi phí điện toán (Snowflake Credits).
  • Dimension Tables: dim_customers, dim_products, dim_territories, dim_calendar (hỗ trợ phân tích thời gian theo Fiscal Year/Quarter).

7. Đảm Bảo Chất Lượng Với 30 Automated dbt Tests & CI/CD

"Không có dữ liệu rác nào được phép lọt vào tầng Gold". Tôi thiết lập hệ thống kiểm thử tự động gồm 30 test cases:

  • Generic Tests: Kiểm tra unique và not_null trên tất cả các khóa chính (Primary Keys và Surrogate Keys).
  • Referential Integrity Tests: Kiểm tra relationships đảm bảo mọi customer_key và product_key trong Fact Sales đều tồn tại hợp lệ trong các bảng Dimension tương ứng (Zero Orphan Records).
  • Singular Business Logic Tests: Viết các custom test SQL kiểm tra số lượng đặt hàng không bao giờ được âm (order_quantity > 0) và ngày đặt hàng không được vượt quá ngày hiện tại.
🚀 Kết Quả Dự Án AdventureWorks Data Platform
  • 23,935 đơn hàng lịch sử được merge chính xác tuyệt đối mà không có bản ghi trùng lặp.
  • 30/30 dbt tests vượt qua tự động trong pipeline CI/CD trước khi triển khai lên môi trường Production.
  • 100% dữ liệu biến động giá bán được lưu vết lịch sử qua SCD Type 2.
  • Dashboard Metabase BI hiển thị tức thì 12 chỉ số KPI kinh doanh cốt lõi (Gross Revenue, Net Margin, Return Rate by Territory, Customer Lifetime Value).
